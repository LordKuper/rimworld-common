ADR-0009 · WorkTypeThingRuleWidget second list — public API form and side-by-side layout

accepted subsystem: project updated 2026-06-07
accepted subsystem: project ADR-0009

Context

WorkTypeThingRuleWidget.DoWidgetTab(...) (Source/LordKuper.Common/UI/Widgets/WorkTypeThingRuleWidget.cs:243–264) is the public integration point for the work-type rule tab and the call site the downstream EquipmentManager mod consumes. Today it carries exactly one items collection (IReadOnlyList<ThingDef> things, List 1) and one thing-box scroll position (ref Vector2 thingIconBoxScrollPosition). There is no parameter through which a consumer can supply on-map Thing instances or enable a second list, and no second scroll state (audit, “Existing implementation found”).

AC-1 requires a public way for a consumer to supply on-map Thing instances and enable rendering of the second list, while AC-4 requires List 1 to remain functional with no regression when the second list is not supplied. The project config sets backward_compat: none, so breaking the public DoWidgetTab signature is permitted — but the break must be documented explicitly (AC-6), recording old and new signatures. The dominant force is therefore: expose the new capability with the smallest call-site change and no new abstraction, since the ASD Simplicity Default forbids introducing a new layer, interface, or options type without explicit Complication Approval, which was not granted.

Decision

Add the second list to the existing DoWidgetTab as two nullable / opt-in parameters: a nullable on-map instance list and a second thing-box scroll position. No overload, no options object, no separate method is introduced.

  • Add an on-map instance list parameter IReadOnlyList<Thing>? mapThings (nullable). When it is null or empty, the second list is not rendered and the bottom section behaves exactly as today — a single ThingDef list — preserving AC-4 and letting existing and other consumers opt in without behavioral change.
  • Add a second thing-box scroll position ref Vector2 mapThingIconBoxScrollPosition so List 2 owns its own scroll state, threaded DoWidgetTab → DoBottomPart symmetrically with the existing thingIconBoxScrollPosition. (Parameter names are illustrative; the implementer may pick equivalent names, but the shape — one nullable IReadOnlyList<Thing> plus one ref Vector2 — is the decision.)
  • This breaks the public DoWidgetTab signature. Permitted under backward_compat: none; the break is documented below (AC-6).

The following architecture-level points follow from this decision and the audit; they bind the implementation:

  • Per-instance tooltip helper (AC-2). Add a new private helper analogous to GetWorkTypeDefTooltip(ThingDef, WorkTypeThingRule) (:317–334) — for example GetWorkTypeThingTooltip(Thing, WorkTypeThingRule) — that reads the real instance's stat values via StatHelper.GetStatValue(Thing, StatDef) (StatHelper.cs:131–155). Unlike the def helper, it must not synthesize a temporary Thing via ThingMaker.MakeThing; it reads the live instance directly, including equippedStatOffsets. It mirrors the existing Current.Game == null early-return guard.
  • Side-by-side layout, constant height (AC-5). The two lists are drawn side by side (horizontally adjacent) within the bottom band — the same arrangement EquipmentManager uses — not stacked vertically. The bottom region is a fixed, non-scrolling band sized by GetBottomPartHeight(int) (:271–275; Tabs.DoTab, Tabs.cs:45–58). Because the second list occupies horizontal space, GetBottomPartHeight is unchanged: it still returns exactly one box height (ThingIconBox.GetThingIconBoxHeight(...)) + one section header + one gap, regardless of whether one list or both are rendered. The band height does not grow for the second list.
  • DoBottomPart splits the band width. DoBottomPart(...) (:38–94) splits the bottom region's width between the two boxes when mapThings is present: List 1 on one side, List 2 on the other, each box on the same row with its own section header directly above it (two headers on a single header row). Each box renders via ThingIconBox.DoThingBox(...) (:54–106, the existing, currently-dormant instance-render primitive for List 2; DoThingDefBox for List 1) with its own scroll position and, for List 2, the new tooltip helper. When mapThings is null/empty, List 1 renders full width exactly as today, at the same band height. Because GetBottomPartHeight never branches on second-list presence, the two functions cannot mis-size the band relative to each other.
  • Width-driven itemsPerRow. Each box computes its itemsPerRow from its own rect.width inside ThingIconBox. When the band is split, each box gets roughly half the width, so it fits fewer items per row and scrolls more internally — this is acceptable and expected; each box scrolls independently within its own region, as today. The shared thingIconBoxRowCount still governs box height, so the box height (and thus the band height) is identical in the one-list and two-list cases.
  • Shared row count. Both lists use the single existing thingIconBoxRowCount parameter; no independent per-list row count is introduced. The audit offers no reason for divergent row counts, and a single shared count keeps the signature minimal and the two boxes visually symmetric. (Were divergent sizing later required, it would be a separate Complication-Approved change.)
  • New strings. The second section needs its own header label and tooltip in Strings.WorkTypeThingRuleWidget alongside the existing AvailableItemsLabel/AvailableItemsTooltip — e.g. AvailableItemsOnMapLabel / AvailableItemsOnMapTooltip (on-map / available-now). Exact wording is an implementation detail; the requirement is two new string entries.
  • Graceful no-op. When mapThings is null or empty, the band width is not split — the second header and box are not drawn and List 1 takes the full width — mirroring the Current.Game == null guard pattern (audit Risk “Current.Game == null / instance availability”).
  • No new tech / dependency. All primitives (DoThingBox, GetThingScore, GetStatValue(Thing, StatDef)) already exist in the assembly; no external dependency is added, so no tech-reference doc is required.

Old vs new DoWidgetTab signature (AC-6)

The signature break is recorded here verbatim so consumers (EquipmentManager) can adapt deliberately. Parameter names on the new collection / scroll arguments are illustrative; the contract is the added types and positions.

Old (before) 
public static void DoWidgetTab(Rect rect, ref float scrollableContentHeight,
    ref Vector2 scrollPosition, int thingIconBoxRowCount,
    IReadOnlyCollection<WorkTypeThingRule> workTypeRules,
    WorkTypeThingRule? selectedWorkTypeRule, Action<WorkTypeThingRule> selectRuleAction,
    Action updateThingsAction, ref Vector2 thingIconBoxScrollPosition,
    IReadOnlyList<ThingDef> things)
New (after) 
public static void DoWidgetTab(Rect rect, ref float scrollableContentHeight,
    ref Vector2 scrollPosition, int thingIconBoxRowCount,
    IReadOnlyCollection<WorkTypeThingRule> workTypeRules,
    WorkTypeThingRule? selectedWorkTypeRule, Action<WorkTypeThingRule> selectRuleAction,
    Action updateThingsAction, ref Vector2 thingIconBoxScrollPosition,
    IReadOnlyList<ThingDef> things,
    ref Vector2 mapThingIconBoxScrollPosition,
    IReadOnlyList<Thing>? mapThings = null)

The added arguments are appended after the existing ones. mapThings is nullable and defaults to null (second list off). Because the second scroll position is a ref Vector2, it cannot carry a default value, so even “List 1 only” callers must pass a backing Vector2 field — this is the source-breaking part of the change and the reason the break is recorded under AC-6.

Consequences

Positive

  • Smallest viable change: the existing method is extended, not duplicated; no new abstraction, layer, interface, options type, or dependency is introduced (honors the Simplicity Default).
  • Opt-in by construction: a null/empty mapThings reproduces today's behavior exactly, so List 1 has no regression path (AC-4) and other consumers adopt the feature only when ready.
  • Symmetric with the existing List 1 plumbing (one collection + one ref Vector2 scroll per list), keeping DoBottomPart uniform and easy to reason about.
  • The dormant DoThingBox primitive is wired up as-is; no new render primitive is needed.
  • Constant bottom-section height: side-by-side layout means GetBottomPartHeight is unchanged and never branches on second-list presence, so the band cannot be mis-sized and the tab layout above it is undisturbed whether one or two lists render.
  • The signature break is explicit and documented, not silent.

Negative

  • Public signature break. The added ref Vector2 (no default possible) forces every DoWidgetTab caller — including List-1-only callers — to update, breaking the EquipmentManager call site. Permitted under backward_compat: none; mitigated by recording old/new signatures (AC-6) and treating consumer adaptation as out of scope (per sprint Non-goals).
  • Growing parameter list. DoWidgetTab goes from 10 to 12 parameters; a long positional signature is harder to read and easy to mis-call. Accepted as the cost of avoiding a new options abstraction the Simplicity Default would otherwise require approval for; revisitable later via Complication Approval if the surface keeps growing.
  • Narrower boxes, more internal scrolling. Because the band width is split, each box gets roughly half the width and computes a smaller itemsPerRow from its rect.width, so each fits fewer items per row and scrolls more internally than a full-width box. This is accepted and expected (each box scrolls independently, as today); the alternative — growing the band — was rejected to keep the bottom-section height constant.
  • New private helper + strings. A per-instance tooltip helper and two new string entries are added; small surface, but they must carry the same Current.Game == null guard and complete the zero-warning build (AC-7).

Alternatives considered

  • Render-options object (e.g. a WorkTypeWidgetOptions struct/class carrying both lists, both scroll positions, and the enable flag) — rejected: introduces a new abstraction/type, which the ASD Simplicity Default forbids without explicit Complication Approval (not granted). It would also force a larger refactor of the existing 10-parameter call path for a single additive feature. The nullable-parameter form delivers the same capability with no new type.
  • Separate method / overload (a second DoWidgetTab that renders two lists) — rejected: duplicates the bottom-section layout and sizing logic across two methods, creating a divergence/regression risk for List 1 and doubling the maintenance surface. A single method with an opt-in parameter keeps one layout path.
  • Independent per-list row counts (a second thingIconBoxRowCount parameter) — rejected for this sprint: adds a parameter with no requirement behind it; the audit gives no reason the two boxes need different row counts. A shared row count is simpler and symmetric; divergent sizing remains available later as a Complication-Approved change.

Acceptance criteria satisfied

  • AC-1 — DoWidgetTab gains a nullable IReadOnlyList<Thing>? mapThings + a second ref Vector2 scroll position; supplying a non-empty list enables the second list, null/empty leaves List 1-only behavior.
  • AC-2 — List 2 renders via ThingIconBox.DoThingBox(...); a new private per-instance tooltip helper reads the live instance's stats via StatHelper.GetStatValue(Thing, StatDef) (no ThingMaker synthesis).
  • AC-4 — with mapThings null/empty, List 1 renders full width at the same band height as today — same items, tooltips, scroll; GetBottomPartHeight is unchanged.
  • AC-5 — the two lists are drawn side by side (disjoint horizontal halves of the band, each with its own header on a single header row); “no overlap” means the boxes occupy disjoint horizontal regions. GetBottomPartHeight does not change — band height is identical for one-list and two-list cases; DoBottomPart splits the band width; both lists share thingIconBoxRowCount (identical box height).
  • AC-6 — the old and new DoWidgetTab signatures are recorded verbatim above; the break is permitted under backward_compat: none.
  • AC-7 — covered by impl/test/build scope: zero-warning rebuild and republish to 1.6/Assemblies/, existing tests pass, the new tooltip helper covered where feasible. This ADR fixes the contracts those criteria verify.

ADR-0010 · WorkTypeThingRuleWidget second list — score-sort ownership (consumer pre-sorts)

accepted subsystem: project updated 2026-06-07
accepted subsystem: project ADR-0010

Context

AC-3 requires List 2 to be displayed in descending score order per the selected rule's stat weights, consistent with WorkTypeThingRule.GetThingScore(Thing) (WorkTypeThingRule.cs:234–242). The open question (sprint PRD, “open decisions”) is who sorts: the widget (calling GetThingScore at render time) or the consumer (supplying an already-sorted list).

The decisive force is the observation-order dependence of scoring. Both GetThingScore and GetThingDefScore normalize through StatRanges, whose NormalizeStatValue maintains a running, expanding per-stat min/max over all items ever scored in the process (WorkTypeThingRule.cs:181–194; audit Risk “Score correctness / order-dependence”). If the widget calls GetThingScore during render, it would feed the on-map instances into that shared range history, perturbing the normalization of both lists every frame — a hidden, render-driven mutation of shared state. List 1 already sidesteps this: the consumer supplies its ThingDef list pre-sorted (the rule's GetGloballyAvailableItems() does items.SortByDescending(GetThingDefScore) at :168–176), and DoThingDefBox renders it purely presentationally.

Decision

The consumer pre-sorts. EquipmentManager supplies the on-map Thing list already sorted by descending score using the public WorkTypeThingRule.GetThingScore(Thing); the widget renders the instance list in the given order and must not re-sort or call GetThingScore during render.

  • List 2 rendering is purely presentational, mirroring DoThingBox's existing contract and List 1, which the consumer also supplies pre-sorted via GetGloballyAvailableItems/GetThingDefScore.
  • GetThingScore is already public (per ADR-0008's exposure work, the instance score path is reachable by the consumer), so the consumer can perform the sort itself.
  • Because the widget never calls GetThingScore at render time, it does not mutate the shared StatRanges observation history during the render pass — no hidden, frame-driven range perturbation.

Consequences

Positive

  • The widget stays free of side effects during render: it does not perturb the shared StatRanges min/max history, so it cannot shift either list's normalization frame-to-frame (audit caveat, WorkTypeThingRule.cs:181–194).
  • Symmetric with List 1: both lists arrive pre-sorted by the consumer and are rendered presentationally, keeping DoBottomPart uniform and the widget's responsibility narrow (render, not compute).
  • AC-3 (descending score order) is satisfied by the consumer's pre-sort using the public GetThingScore; relative best-first order within the list holds regardless of the order-dependent absolute normalization.
  • The consumer already owns the on-map collection logic (sprint Non-goals), so it is the natural place to also own the sort — no new responsibility is pushed into the widget.

Negative

  • Trust boundary. The widget cannot guarantee AC-3 on its own; if the consumer supplies an unsorted list, the display order is wrong. The widget renders what it is given. Mitigated by documenting the pre-sort contract on the public parameter (XML doc) so the obligation is explicit at the call site.
  • AC-3 is not unit-testable inside the widget. Because the widget does not sort, there is no in-widget sort to assert; coverage targets GetThingScore ordering directly (AC-7, “where feasible”), and the widget-render path stays as the hard-to-unit-test IMGUI surface the audit already flagged.
  • Order-dependence caveat still exists for the consumer. Whichever side sorts must accept that absolute normalized values depend on what else has been scored in the process; only relative order within the list is stable. This is inherent to the ADR-0002 adaptive contract and is documented, not introduced here.

Alternatives considered

  • Widget sorts via GetThingScore at render time — rejected: calling GetThingScore on the on-map instances during the render pass feeds them into the shared, process-global StatRanges min/max history every frame, perturbing the normalization of both lists (a hidden render-driven mutation of shared state). It also breaks symmetry with List 1, which the consumer already supplies pre-sorted. Pre-sorting by the consumer keeps render side-effect-free.
  • Widget sorts a defensive copy without touching shared ranges — rejected: there is no order-independent score path; GetThingScore normalizes through the shared StatRanges by design (ADR-0002), so any in-widget scoring still observes/extends that shared history. A non-mutating score would be a separate, out-of-scope redesign of the normalizer (explicitly out of scope; ADR-0002 blessed the order-dependence).

Acceptance criteria satisfied

  • AC-3 — the consumer pre-sorts the instance list by descending GetThingScore; the widget renders in the given order and does not re-sort. Relative best-first order holds despite order-dependent normalization.
  • AC-7 — GetThingScore ordering is covered directly where feasible; the widget-render path remains the IMGUI surface the audit flagged as hard to unit-test. This ADR fixes the ownership contract that scope verifies.

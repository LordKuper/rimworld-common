ADR-0006 · RimWorld AssemblyResolve seam: [assembly: TestFramework] → global [SetUpFixture]

approved subsystem: project updated 2026-06-04
approved subsystem: project ADR-0006

Context

Most of the suite references RimWorld/Unity types. The library does not ship those assemblies; instead an AppDomain.CurrentDomain.AssemblyResolve handler resolves them at runtime from the RimWorld install (%RIMWORLD_DIR%/%RimWorldDir% → RimWorldWin64_Data\Managed\<name>.dll via Assembly.LoadFrom). Under xUnit this handler is wired through the framework-swap hook ([assembly: TestFramework("…RimWorldTestFramework", …)] in AssemblyInfo.cs + RimWorldTestFramework : XunitTestFramework, whose constructor calls InitializeRimWorldResolver() before any discovery). NUnit has no analog to [assembly: TestFramework]. The load-bearing constraint is timing: the resolver MUST be registered before any RimWorld-typed test class is JIT-resolved, or those tests fail at discovery/first-touch with FileNotFoundException/TypeLoadException — which presents as mass test failure, not a wiring bug (audit risk; PRD AC-19 … AC-21). The coverage harness depends on this too: scripts/coverage.ps1 step 3 deletes the copied RimWorld DLLs precisely so the runtime resolver reloads them lazily.

Decision

Replace the xUnit framework-swap hook with a namespace-less (global) [SetUpFixture] whose [OneTimeSetUp] registers the same AssemblyResolve handler, preserving the resolution contract verbatim.

  • Delete the [assembly: TestFramework(...)] attribute from AssemblyInfo.cs and the RimWorldTestFramework : XunitTestFramework type. Rename XunitExtensions.cs (no longer "Xunit") and re-house the resolver in a namespace-less [SetUpFixture] class. A [SetUpFixture] declared outside any namespace applies to the whole assembly; its [OneTimeSetUp] runs once before any test in the assembly is executed — the timing guarantee that replaces the xUnit framework-constructor hook (AC-19).
  • Chosen timing guarantee. NUnit invokes the global [SetUpFixture]'s [OneTimeSetUp] before constructing or running any test fixture. Registering the AssemblyResolve handler there is asserted to make it live before the first RimWorld-typed test type is resolved at execution time.
  • Resolution contract preserved verbatim (AC-20): the assembly-name match set (Assembly-CSharp, Assembly-CSharp-firstpass, UnityEngine*, Unity.Burst, Unity.Collections, Unity.Mathematics, com.rlabrecque.steamworks.net); the env-var lookup (RIMWORLD_DIR/RimWorldDir) with the existing fallback behavior; the Managed\<name>.dll Assembly.LoadFrom resolution; and the null-for-everything-else contract. None of these change — only the registration mechanism does.
  • Idempotency guard retained — justified by the contingency. The previous AppDomain.GetData/SetData("RimWorldResolverInitialized") guard is kept. Its rationale is no longer "redundant but harmless / in case we need it": the accepted-risk contingency below makes a second registration path a concrete anticipated case — if the [ModuleInitializer] fallback is added later, both it and the [OneTimeSetUp] could attempt registration in the same process, so a guard that makes registration once-only across any path is justified defensive code, not a smell.
  • Verification. Confirm the resolver is live before type load by running the RimWorld-typed suites (StatWeightTests, RimWorldTimeTests, PawnFilterTests) and confirming no FileNotFoundException/ TypeLoadException at discovery/execution (AC-21), and by re-running scripts/coverage.ps1 end-to-end so the step-3 DLL-removal + lazy-resolve path still cooperates (AC-27).
  • The [SetUpFixture] seam is not a new abstraction — it is the NUnit-idiomatic replacement for an existing seam; the resolver logic is reused. No Complication Approval beyond the framework swap (ADR-0004) is required.

Accepted risk (external review, design-phase decision)

The external (Codex) review flagged that [OneTimeSetUp] runs at NUnit execution time and does not provably precede discovery-time type loading: NUnit can JIT-resolve a test type while building its fixture model before any [OneTimeSetUp] body has run. The AC-20 "resolver-before-type-load" ordering guarantee is therefore asserted, not proven. The user accepted this risk for the design phase and chose to keep the [SetUpFixture]/[OneTimeSetUp] mechanism, revisiting only if the problem actually manifests in impl.

Documented contingency (anticipated fallback path): if discovery-time RimWorld type resolution fails during implementation, fall back to an earlier registration mechanism — e.g. a [ModuleInitializer] (with a net472 IsExternalInit/attribute polyfill) that registers the resolver at module load, before NUnit touches any test type. This is now an anticipated path, not a contingency invented on failure. The retained idempotency guard (above) is what makes the [ModuleInitializer] + [OneTimeSetUp] coexistence safe should the fallback be adopted.

Consequences

Positive

  • Restores the load-bearing "resolver-before-type-load" guarantee using a documented NUnit lifecycle hook, with a contract verbatim-identical to the xUnit version.
  • Removes the xUnit-only [assembly: TestFramework] coupling; the seam is now expressed in plain NUnit constructs that any maintainer can read.
  • The coverage harness's lazy-resolve dependency keeps working unchanged because the resolution contract is preserved.

Negative

  • Highest-risk piece of the migration. If the global [SetUpFixture] is accidentally placed inside a namespace, it scopes to that namespace only and runs too late for tests elsewhere — re-introducing the JIT-resolution failures as apparent mass test failure. The namespace-less placement is a hard requirement, not a style choice.
  • Ordering is asserted, not proven (accepted risk). The external review noted that [OneTimeSetUp] runs at execution time and does not provably precede discovery-time type loading, so the AC-20 ordering guarantee is asserted. The user accepted this for the design phase; the anticipated fallback is an earlier registration via [ModuleInitializer] (net472 attribute polyfill) if discovery-time resolution actually fails in impl. Pinning NUnit 4.6.1 (ADR-0004) further bounds any future ordering drift.
  • The handler mutates process-global AppDomain state; the retained idempotency guard is justified defensive code (not overhead) because the accepted-risk contingency makes a second registration path — the [ModuleInitializer] fallback alongside [OneTimeSetUp] — a concrete anticipated case.
  • Supersedes the XunitExtensions.cs/AssemblyInfo.cs wiring; the rename + attribute deletion is a behavior-sensitive edit that must be verified by actually running the RimWorld-typed suites, not by inspection alone.

Alternatives considered

  • Module initializer ([ModuleInitializer]) — not chosen now, but retained as the anticipated fallback (see Accepted-risk note). It registers the resolver at module load, earlier than [OneTimeSetUp], so it would address the discovery-time ordering gap the external review flagged; it needs a net472 attribute polyfill and is harder to verify than an explicit [OneTimeSetUp]. The global [SetUpFixture] is the NUnit-sanctioned hook and is preferred while the asserted ordering holds; the user accepted the risk of keeping it and moving to [ModuleInitializer] only if discovery-time resolution actually fails in impl.
  • Per-fixture [OneTimeSetUp] on each RimWorld-typed test class — rejected: duplicative, easy to forget on a new test class (silent regression), and still per-class rather than assembly-global; the single global fixture is the minimal, centralized seam.
  • Copy the RimWorld DLLs next to the test output instead of resolving at runtime — rejected: changes the coverage harness's deliberate step-3 DLL-removal design and bloats the output; the runtime resolver is the established, intentional approach.

Acceptance criteria satisfied

  • AC-19 — the resolver is wired through a namespace-less global [SetUpFixture]/[OneTimeSetUp] that runs once before any test executes.
  • AC-20 — the resolution contract (assembly-name match set, env-var lookup + fallback, Managed\<name>.dll LoadFrom, null-for-others) is preserved verbatim; the ordering guarantee is asserted (see Accepted risk).
  • AC-21 — verified by running the RimWorld-typed suites with no FileNotFoundException/TypeLoadException.
  • AC-27 — the coverage harness's step-3 DLL-removal + lazy-resolve path still cooperates after the resolver port.

PRD — 003-statranges-fix-expose

3 goals 5 stories 10 AC 1 non-goal updated 2026-06-06

Problem

The shared StatRanges normalizer mishandles the first observation of every stat, and the type is hidden behind internal so the downstream EquipmentManager mod cannot consume it.

Two coupled defects in Source/LordKuper.Common/StatRanges.cs block the library from being a correct, reusable normalization primitive:

  • First-observation bug (UpdateStatRange, lines 53–66). On a TryGetValue miss the dictionary entry is correctly seeded to [value, value], but the local range variable keeps its default(FloatRange) value {0, 0}. The subsequent min/max comparisons run against that stale local and overwrite the seeded entry. The first value v therefore yields [0, v] for a positive v (or [v, 0] for a negative v) instead of the correct degenerate range [v, v]. Downstream, MathHelper.NormalizeValue turns a correct [50, 50] (which should normalize 50 → 0) into a buggy [0, 50] (which normalizes 50 → 1), so scores for first-observed stats are wrong.
  • Hidden surface. StatRanges and NormalizeStatValue are internal. The EquipmentManager mod cannot reference the shared, corrected implementation and instead maintains its own duplicate range logic (EquipmentManagerGameComponent_StatRanges) that carries the same class of error.

The existing test suite does not catch the bug: all six tests in StatRangesTests.cs assert only !NaN && !Inf, so they pass under both buggy and fixed code and do not lock in the contract.

Audience & consumers

  • Mod developers consuming LordKuper.Common — primarily the downstream EquipmentManager mod. Making Common.StatRanges correct and public is the prerequisite for that mod to drop its duplicate range logic and consume the shared implementation. (The migration of EquipmentManager itself is motivating context only and is out of scope — see Non-goals.)
  • In-library consumer WorkTypeThingRule — GetThingDefScore and GetThingScore are the only production callers of StatRanges.NormalizeStatValue. They rely on the static, process-global range cache accumulating min/max across all scored defs and things. The fix corrects the scores they emit for first-observed stats but does not change the NormalizeStatValue(StatDef, float) signature, so these callers are not edited.

Goals

  1. G1

    Correct the first-observation behavior so the first value v of any stat produces the degenerate range [v, v] and normalizes consistently.

  2. G2

    Expose StatRanges as a public, reusable primitive (public class, public NormalizeStatValue, public Clear()) while preserving its intentional static / process-global adaptive design.

  3. G3

    Lock in the corrected contract with revert-sensitive tests and ship the corrected behavior by republishing the assembly with a clean (zero-warning) build.

User stories

Mod developer (Common consumer) 2
  • as a mod developer consuming LordKuper.Common, I want StatRanges and NormalizeStatValue to be public with a stable signature and a Clear() reset entry point, so that I can reference the shared normalizer directly and drop my own duplicate range logic. → AC-3, AC-4, AC-5
  • as a mod developer consuming LordKuper.Common, I want the first observation of a stat to normalize correctly, so that the scores I derive from the shared primitive are right from the first value. → AC-1, AC-2
Library maintainer 2
  • as the library maintainer, I want the static / process-global adaptive design preserved (not converted to an instance class), so that the existing WorkTypeThingRule consumer keeps accumulating min/max across all scored items as intended. → AC-6
  • as the library maintainer, I want the corrected behavior pinned by exact-bound regression tests and the shipped assembly rebuilt cleanly, so that the fix cannot silently regress and consumers receive the corrected binary. → AC-7, AC-8, AC-9, AC-10
Test engineer 1
  • as the test engineer, I want the static-state reset in StaticStateTestBase to route through the new public StatRanges.Clear() instead of reflection on the Ranges field, so that cross-test isolation no longer depends on a stringly-typed field lookup that breaks on rename. → AC-5, AC-7

Acceptance criteria

Each criterion is one testable assertion. They map 1:1 onto the sprint acceptance items in sprint.md.

IDCriterionAreaPriority
AC-1On a TryGetValue miss, UpdateStatRange seeds a local FloatRange(value, value), runs both min/max comparisons against that seeded value (never the stale {0, 0} default), and writes the dictionary entry exactly once; the first value v for any stat yields the range [v, v].bug fixmust
AC-2With first v = 50, NormalizeStatValue(stat, 50) returns 0 (degenerate [50, 50]) and a later NormalizeStatValue(stat, 100) returns 1; for the sequence -10, -5, 0 the range becomes [-10, -5] then [-10, 0], with -10 → 0 and 0 → 1.behaviormust
AC-3StatRanges changes from internal static class to public static class.visibilitymust
AC-4NormalizeStatValue changes from internal static to public static, keeping the signature exactly NormalizeStatValue(StatDef, float).visibilitymust
AC-5A public static void Clear() => Ranges.Clear(); member exists on StatRanges, and StaticStateTestBase resets the range cache by calling StatRanges.Clear() instead of reflecting the Ranges backing field.visibilitymust
AC-6StatRanges remains static and process-global; it is NOT converted to an instance class, and the WorkTypeThingRule consumer continues to accumulate min/max across all scored items via the shared cache.constraintmust
AC-7StatRangesTests.cs contains exact-bound assertions (first v = 50 → [50, 50] with 50 → 0 / 100 → 1; sequence -10, -5, 0 → [-10, -5] → [-10, 0] with -10 → 0 / 0 → 1) using the existing FakeDefProvider + StatHelper.Rebuild() pattern.testsmust
AC-8A named regression test (e.g. NormalizeStatValue_FirstPositiveValue_SeedsDegenerateRange) exists that passes on the fix and demonstrably fails if the fix is reverted to the old [0, v] behavior.testsmust
AC-9The solution builds green with 0 warnings (high warning level + warnings-as-errors), and all existing plus new tests pass.buildmust
AC-10The corrected Common assembly is rebuilt from the fixed source and republished to 1.6/Assemblies/ (net472 output landing in the version folder).publishmust

UI / UX

N/A — headless library, no UI surface. LordKuper.Common is a RimWorld modding library consumed as an assembly; this sprint has no user-facing screens, flows, or visual design. UX-spec, mockups, and design-system steps are skipped for this sprint by user decision.

Non-goals

  • Migrating the EquipmentManager mod itself onto Common.StatRanges / Common.WorkTypeThingRule and deleting its duplicate range logic (EquipmentManagerGameComponent_StatRanges). That is motivating context for exposing the type, but the migration is a separate, future effort outside this sprint.

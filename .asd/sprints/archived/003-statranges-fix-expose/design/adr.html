ADR-0008 · StatRanges first-observation fix and public-API exposure

proposed subsystem: project updated 2026-06-06
proposed subsystem: project ADR-0008

Amends ADR-0002 and ADR-0007. This decision changes facts those approved ADRs assert: ADR-0002 describes NormalizeStatValue as internal static and states “no signature or runtime-behavior change to any public member” (both become false here — visibility flips to public and first-observation behavior is corrected), and ADR-0007 describes the test-isolation reset of StatRanges.Ranges as a reflection-null of the backing field (this decision routes that reset through the new public StatRanges.Clear()). The wording reconciliation of ADR-0002 and ADR-0007 is design-promote work, not part of this ADR's decision; this ADR records the superseding clauses, and design-promote remaps the prose in those persistent files in place.

Context

Source/LordKuper.Common/StatRanges.cs is the shared per-StatDef stat normalizer. Its adaptive running-min/max contract was blessed by ADR-0002 and its static cache is part of the test-isolation snapshot/restore set defined by ADR-0001 and re-expressed for NUnit in ADR-0007. Three forces drive this sprint (see audit.md and prd.html):

  • Confirmed correctness defect. In UpdateStatRange (StatRanges.cs:53–66), on a TryGetValue miss the dictionary entry is seeded to [value, value], but the local range variable keeps its default(FloatRange) value {0, 0}. The subsequent min/max comparisons run against that stale local and overwrite the seeded entry. The first value v therefore yields [0, v] for positive v (or [v, 0] for negative v) instead of the correct degenerate [v, v]. Through MathHelper.NormalizeValue this makes NormalizeStatValue(stat, 50) return 1 where 0 is correct. The existing six tests assert only !NaN && !Inf, so they pass under both buggy and fixed code and never lock the contract.
  • Hidden surface blocks reuse. StatRanges and NormalizeStatValue are internal. The downstream EquipmentManager mod cannot reference the shared, corrected implementation and instead carries its own duplicate range logic (EquipmentManagerGameComponent_StatRanges) with the same class of error. Making the type correct and public is the prerequisite for that mod to drop its duplicate (the migration itself is out of scope — motivating context only).
  • Stringly-typed reset fragility. StaticStateTestBase (:107–111) resets the cache by reflecting the Ranges field by the literal name "Ranges". A future rename would silently no-op the reset and leak state across the suite. The newly public surface offers a typed reset entry point to replace it.

The project config sets backward_compat: none, so future breaking changes to a public surface are permitted without ceremony; nonetheless, promoting members to public is a deliberate commitment that should be acknowledged and documented, not made implicitly.

Decision

Correct the first-observation logic, expose StatRanges and NormalizeStatValue as public with a new public Clear(), keep the type static and process-global, and route the test-isolation reset through Clear().

D1 — Correct first-observation to seed a degenerate [v, v] range

Rewrite UpdateStatRange so that on a TryGetValue miss it seeds a local FloatRange(value, value), runs both the min and max comparisons against that seeded value (never the stale {0, 0} default), and writes the dictionary entry exactly once. The first value v for any stat then yields [v, v]. This is not a behavioral redesign — it is the realization of the adaptive-normalization contract ADR-0002 already blessed: the running min/max is intended to begin from the first observed value, so a single observation must produce a degenerate range that normalizes to 0. The current code merely compares against an accidental {0, 0} seed; D1 removes that accident. (PRD AC-1, AC-2.)

D2 — Expose StatRanges and NormalizeStatValue as public; add public Clear()

Change internal static class StatRanges to public static class; change internal static float NormalizeStatValue(...) to public static, keeping the signature exactly NormalizeStatValue(StatDef, float) (unchanged); and add public static void Clear() => Ranges.Clear();. The downstream EquipmentManager mod then consumes the shared, corrected primitive instead of duplicating it. This is now a public-API surface commitment: the adaptive/order-dependent contract from ADR-0002 must be documented on the now-public members via XML docs. With backward_compat: none, future breaks are allowed without ceremony, but the commitment is acknowledged here so the surface is adopted deliberately. (PRD AC-3, AC-4, AC-5.)

D3 — Keep StatRanges static and process-global (NOT an instance class)

StatRanges remains static with its process-global Ranges cache; it is explicitly not converted to an instance class. The only production consumer, WorkTypeThingRule (GetThingDefScore / GetThingScore), relies on the shared cache to accumulate min/max across all scored defs and things within the process — the adaptive design ADR-0002 documents as intentional. Converting to an instance class would fragment that accumulation and break the documented contract. Exposing the existing static type (D2) is sufficient for the downstream consumer; no instance abstraction is introduced. (PRD AC-6.)

D4 — Route the test-isolation reset through the public Clear()

Replace the reflection-null of the Ranges backing field in StaticStateTestBase (:107–111) with a direct StatRanges.Clear() call. This removes the stringly-typed "Ranges" field lookup, eliminating the rename-fragility risk while preserving the exact isolation contract ADR-0007 defines (the StatRanges.Ranges entry stays in the reset set; only its mechanism changes from reflection to a typed call). (PRD AC-5.)

Consequences

Positive

  • First-observed stats normalize correctly ([v, v] → 0), realizing the ADR-0002 adaptive contract that the buggy {0, 0} seed silently violated.
  • The downstream EquipmentManager mod can consume one correct shared primitive instead of duplicating range logic that carried the same defect.
  • The signature NormalizeStatValue(StatDef, float) is unchanged, so the in-library WorkTypeThingRule consumer is not edited and other callers are source-compatible.
  • The typed StatRanges.Clear() reset removes the stringly-typed "Ranges" reflection lookup, closing the rename-fragility hole in StaticStateTestBase.
  • No new abstraction, layer, interface, or dependency is introduced; the existing static type is reused as-is (only visibility and one tiny member change).

Negative

  • Public-API commitment. Promoting StatRanges + NormalizeStatValue + Clear() to public makes them a contract surface consumed by EquipmentManager. backward_compat: none permits future breaks without ceremony, but the surface is now something consumers depend on. Mitigation: keep the signature unchanged and document the adaptive/order-dependent contract on the public members.
  • Behavior shift for existing consumers. WorkTypeThingRule scores change for first-observed stats (degenerate [v, v] → 0 instead of the buggy [0, v] → nonzero). This is the intended correction, but it changes emitted scores; the new exact-bound tests lock the corrected values.
  • Warnings-as-errors discipline. The build uses a high warning level with warnings-as-errors. New public members with incomplete XML docs, or any unused/dead local in the rewritten UpdateStatRange, fail the build. Mitigation: full XML docs on the now-public members and Clear(); no dead locals in the rewrite.
  • Assembly republish gate. The shipped 1.6/Assemblies/ artifact must be rebuilt from the fixed source; shipping corrected source against a stale assembly is a silent regression for consumers. Mitigation: treat rebuild-and-publish to 1.6/Assemblies/ as a hard acceptance gate after green tests.
  • Approved-ADR drift. ADR-0002 and ADR-0007 now read as out-of-date (see Amends note). Their prose reconciliation is deferred to design-promote; until then the persistent ADRs lag the as-built result.

Alternatives considered

  • Convert StatRanges to an instance class — rejected: the process-global accumulation across all scored items in WorkTypeThingRule is the documented adaptive design (ADR-0002); per-instance ranges would fragment that accumulation and silently change scoring. Exposing the existing static type meets the consumer's need without the redesign.
  • Keep StatRanges internal and let EquipmentManager keep its own copy — rejected: leaves two divergent implementations of the same primitive, both carrying the first-observation defect, and defeats the sprint's reuse goal. The whole point is one correct shared normalizer.
  • Fix the bug in place by also mutating the seeded entry (write twice) — rejected: writing the dictionary entry on both the seed and the comparison path is redundant and easy to get subtly wrong; seeding a local and writing exactly once is simpler and provably correct.
  • Leave the reflection-null reset in StaticStateTestBase — rejected: the literal "Ranges" field lookup silently no-ops on rename and leaks state across the suite. Since a typed public Clear() now exists, routing the reset through it is strictly safer at no cost.
  • Make NormalizeStatValue deterministic / order-independent — rejected: out of scope and already explicitly rejected by the user in ADR-0002, which blesses the adaptive order-dependence as the intended contract.

Acceptance criteria satisfied

  • AC-1 — D1: UpdateStatRange seeds a local FloatRange(value, value) on miss, compares against it, writes once; first value v yields [v, v].
  • AC-2 — D1: corrected normalization (first v=50 → 0; later 100 → 1; sequence -10, -5, 0 → [-10, -5] then [-10, 0] with -10 → 0 / 0 → 1).
  • AC-3 — D2: StatRanges becomes public static class.
  • AC-4 — D2: NormalizeStatValue becomes public static with the unchanged signature NormalizeStatValue(StatDef, float).
  • AC-5 — D2 + D4: public static void Clear() => Ranges.Clear(); exists and StaticStateTestBase resets via StatRanges.Clear() instead of reflecting the Ranges field.
  • AC-6 — D3: StatRanges stays static / process-global; not an instance class; WorkTypeThingRule keeps accumulating min/max across all scored items.
  • AC-7, AC-8, AC-9, AC-10 — covered by the impl/test/build scope (exact-bound and revert-sensitive tests, zero-warning build, republish to 1.6/Assemblies/); this ADR fixes the contract those criteria verify.

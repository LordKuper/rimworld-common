Scope & dropped decisions

This sprint draft records three accepted architecture decisions arising from the full-project audit of LordKuper.Common. They establish a testability seam around RimWorld Verse access (ADR-0001), pin down the contract of the adaptive stat-range normalization (ADR-0002), and consolidate build governance across the solution (ADR-0003).

No new external technology is introduced by any decision in this document (no provider library, no test framework change beyond the already-present xUnit, no new runtime or service). Therefore no tech-reference/ additions or updates are required.

Considered and not pursued

An earlier draft proposed a fourth ADR (former ADR-A) to make the WorkType→Stat default-weight surface data-driven, on the theory that the hardcoded weights in WorkTypeStatMap were a prohibited hardcoded-balance violation. This was dropped. The user determined that those default weights are intentional seed defaults: consuming mods override them through their own persisted settings (the IExposable StatWeight / WorkTypeThingRule objects), so the seeds are configuration starting points, not fixed balance baked into the library. They are not an architectural concern and need no ADR.

The only change retained for that area is a non-architectural code fix, recorded here for traceability but requiring no decision record: WorkTypeStatMap will emit Logger.LogWarning (including worktype and stat context) when a referenced StatDef resolves to null through GetNamedSilentFail, instead of silently no-op'ing. This is captured as an audit/implementation item, not an ADR.

accepted subsystem: sprint ADR-0001

ADR-0001 · RimWorld-context isolation seam

Context

LordKuper.Common reaches directly into RimWorld's Verse layer through static DefDatabase<T> lookups and WorkTypeDefsUtility from numerous call sites (StatHelper, WorkTypeStatMap, WorkTypeThingRule, DefCache, StatWeight, PassionHelper). Several of these sites run inside static constructors, building caches at type-load time. Because the data source is a global static owned by the running game, the library is effectively impossible to unit-test in isolation: there is no seam at which a test can supply controlled defs, and the load-time caches retain process-global state that leaks between tests. This blocks the sprint's coverage goal (≥80%) and its static-isolation acceptance criteria.

Decision

Introduce a single IDefProvider abstraction with a static DefProvider.Current injection point, and route all direct Verse def access through it.

  • Define IDefProvider as the one seam for def/worktype resolution. The default implementation, VerseDefProvider, delegates to DefDatabase<T> and WorkTypeDefsUtility exactly as today. Tests install a FakeDefProvider.
  • Reroute the direct DefDatabase<T> call sites (StatHelper, WorkTypeStatMap, SkillStatMap, WorkTypeThingRule, DefCache, StatWeight, PassionHelper) through DefProvider.Current. SkillStatMap is listed here for consistency with the PRD static-cache snapshot set (AC-15/AC-16): any DefDatabase resolution it performs goes through the same seam; if a given build of SkillStatMap performs no direct DefDatabase call, its only obligation is snapshot/restore, but it remains in this list so the ADR and PRD agree on the surface.
  • Extract the static-constructor bodies of StatHelper and WorkTypeStatMap into internal static Rebuild() methods, called by both the static constructor (preserving load-time behavior exactly) and by test fixtures that need to rebuild against a fake provider.
  • Documented exception to the “no static constructors with heavy side effects” rule (.asd/project/custom-design-rules.md · Modding & patchability). The Rebuild() extraction keeps the DefDatabase-walking work invoked from the static constructors; the heavy load-time initialization is therefore retained, not removed. This is a deliberate, bounded exception, recorded here for traceability:
    • Load-time DefDatabase initialization is idiomatic RimWorld — static-ctor / [StaticConstructorOnStartup] init is the canonical way mods hook game load, so the work belongs at type-load by design.
    • It is guarded and runs exactly once per process, and it satisfies the project's Fail-Fast-on-Load expectation (see AC-24: static-init paths emit clear Logger context on failure).
    • The Rebuild() extraction adds a test-time re-init path without changing load-time behavior; no new heavy static work is introduced.
    • The exception is intentional and bounded to these existing init paths (StatHelper, WorkTypeStatMap); it does not license any new heavy static initialization elsewhere in the codebase.
  • Add [assembly: InternalsVisibleTo] for the Tests assembly, exposing the internal reset/snapshot/Rebuild() hooks.
  • Add an xUnit StaticStateFixture (used via IClassFixture plus a [Collection] to serialize across classes that touch shared statics). It snapshots and restores the static caches: StatHelper, WorkTypeStatMap, SkillStatMap, PassionHelper, the DefCache statics, and StatRanges.Ranges — the latter explicitly, because ADR-0002 keeps that cache mutable (see ADR-0002).
  • The new IDefProvider abstraction and the InternalsVisibleTo grant were approved by the user under Complication Approval, granted 2026-06-03.

Consequences

Positive

  • Creates the single test seam that unblocks unit testing of the core helpers and gates the ≥80% coverage goal.
  • Production behavior is unchanged: VerseDefProvider is a thin pass-through and remains the default.
  • Centralizes all Verse def access behind one interface, simplifying future changes to def resolution.
  • The snapshot/restore fixture makes static-state leakage between tests deterministic and explicit.

Negative

  • Adds a new abstraction (IDefProvider) and a mutable global injection point (DefProvider.Current) — a global the rest of the codebase must respect.
  • InternalsVisibleTo widens the internal surface to the Tests assembly; internal reset/snapshot hooks become a maintained contract.
  • Static-ctor extraction into Rebuild() is behavior-sensitive: it MUST reproduce load-time ordering exactly, or load-time semantics drift.
  • Cross-class test serialization via [Collection] reduces test parallelism for the affected suites.
  • Behavioral/API note: no public-API break in production paths; the new public/injectable seam is additive. The reset/snapshot hooks are internal, not part of the public mod API.

Alternatives considered

  • Per-class constructor injection of a provider — rejected: the affected statics build caches at type-load time with no instance to inject into; a static injection point is the minimal seam that fits the existing static design.
  • Wrapping DefDatabase<T> only at test time via a shim/mocking framework — rejected: would not give a stable production seam and would still leave load-time static caches un-resettable between tests.

Acceptance criteria satisfied

  • AC-13 — provides the RimWorld-context isolation seam that lets stateful subsystems run without a live DefDatabase/game context.
  • AC-14, AC-15 — the StaticStateFixture save/restores the shared static caches (StatHelper, WorkTypeStatMap, SkillStatMap, StatRanges, PassionHelper, and the DefCache statics) around each test.
  • AC-16 — the snapshot set explicitly includes the adaptive StatRanges.Ranges cache retained under ADR-0002.
  • AC-18 — records the isolation-seam approach in an ADR before broad test build-out.
  • AC-19 — the snapshot/restore makes the suite pass order-independently with no inter-test state leakage.
  • AC-24 — the retained static-init paths walking the DefDatabase emit clear Logger context on failure, consistent with Fail-Fast-on-Load.
  • Gates AC-20 and AC-21 — the seam is the prerequisite that enables the comprehensive stateful-subsystem tests and the ≥80% Coverlet line-coverage floor.

Related ADRs

  • ADR-0002: ADR-0002 keeps StatRanges.Ranges mutable, which is exactly why this ADR's fixture must snapshot/restore it.

ADR-0002 · StatRanges normalization — documented adaptive contract

Context

StatRanges.NormalizeStatValue normalizes a stat value against a running min/max range maintained per StatDef in the static StatRanges.Ranges cache. Because the range adapts as values are observed, the normalized score for a given item depends on the set and order of items scored so far in the current process. This propagates into WorkTypeThingRule.GetThingScore and WorkTypeThingRule.GetThingDefScore. The audit flagged this as a reproducibility/observation-order concern: identical inputs can yield different scores depending on history. A decision was needed on whether to make normalization deterministic or to keep — and formally bless — the adaptive behavior.

Decision

Keep the running min/max adaptive normalization (option b). Do not make it deterministic. Instead, document the observation-order dependence as the intended contract.

User-approved deviation from a named project rule. Keeping the order- and history-dependent scoring is an explicit, user-approved exception to the .asd/project/custom-design-rules.md · Determinism rule (“same inputs → same outputs; no time- or order-dependent behavior in core logic unless explicitly required”) and to code-style §11. The deviation is recorded here against that named rule: the order-dependence is the explicitly required behavior for this stat normalization, and is made discoverable via XML docs rather than removed.

  • StatRanges.NormalizeStatValue continues to mutate the per-StatDef Ranges cache as values are observed. No behavioral change.
  • Add explicit XML doc comments to the affected public members (StatRanges.NormalizeStatValue, WorkTypeThingRule.GetThingScore, WorkTypeThingRule.GetThingDefScore) stating that the returned scores are adaptive and depend on the set and order of items scored within the current process. This makes the order-dependence a documented, intentional contract rather than a latent surprise.
  • No reproducibility test is required: the adaptive behavior is the documented contract, so there is nothing deterministic to assert.

Consequences

Positive

  • Zero behavioral change — existing mods relying on current scoring behavior are unaffected.
  • The order-dependence becomes explicit and discoverable in the public API docs.
  • Avoids the risk and churn of redesigning normalization for determinism.

Negative

  • Scores remain non-reproducible across differing observation histories; consumers must understand the documented adaptive contract.
  • The static StatRanges.Ranges cache stays — process-global mutable state that must be saved/restored by ADR-0001's StaticStateFixture for tests to remain isolated. This cross-cutting obligation is the cost of keeping the cache.
  • Behavioral/API note: only XML documentation changes; no signature or runtime-behavior change to any public member.

Alternatives considered

  • Option (a): deterministic normalization — making NormalizeStatValue order-independent (e.g. precomputed or fixed ranges) — explicitly rejected by the user in favor of preserving existing runtime behavior. Determinism would have changed observable scores for current consumers and was judged not worth the behavioral break.

Acceptance criteria satisfied

  • AC-9 — documents the observation-order dependence on the affected public members' XML docs (StatRanges.NormalizeStatValue, WorkTypeThingRule.GetThingScore, GetThingDefScore), with the adaptive behavior retained by design (no behavioral change).
  • AC-16 — formally requires the retained adaptive StatRanges.Ranges cache to be in ADR-0001's snapshot/restore set, so order-independence (AC-19) holds despite the documented order-dependent scoring.

Related ADRs

ADR-0003 · Solution-wide build governance

Context

Build governance was applied only at Source/Directory.Build.props, which also carried RimWorld-path resolution. As a result the Tests project did not inherit the strict policy (TreatWarningsAsErrors, elevated warning level, nullable), leaving a governance gap. Additionally, RimWorld path resolution fell back to a hardcoded d:\Games\... default, which silently masks misconfiguration on machines where that path does not exist. The audit required a single source of truth for build policy that covers both Source and Tests, plus fail-fast behavior when the game directory cannot be resolved.

Decision

Introduce a repo-root Directory.Build.props as the single governance SSoT, and make RimWorld path resolution fail fast.

  • Add Directory.Build.props at the repository root hoisting TreatWarningsAsErrors=true, WarningLevel=9999, and Nullable=enable so both Source and Tests inherit them (closing the Tests-project policy gap).
  • Source/Directory.Build.props keeps only the RimWorld-path resolution and must inherit the root props via an explicit import. MSBuild auto-imports only the nearest Directory.Build.props, so Source/Directory.Build.props would otherwise shadow the repo-root file rather than chain to it. Add an explicit import near the top of Source/Directory.Build.props: 
    <Import Project="$([MSBuild]::GetPathOfFileAbove('Directory.Build.props', '$(MSBuildThisFileDirectory)../'))" />
    so the root governance props (TreatWarningsAsErrors, WarningLevel, Nullable) are actually inherited by the Source project. The Tests project has no child Directory.Build.props, so it inherits the repo-root file automatically via the standard nearest-file auto-import and needs no explicit import.
  • No LangVersion pin. The user explicitly rejected pinning to 13.0; LangVersion stays latest.
  • RimWorld path fail-fast: remove the hardcoded d:\Games\... default. If neither RIMWORLD_DIR nor RimWorldDir resolves to an existing directory, emit a clear MSBuild build error. RIMWORLD_DIR is the documented override.
  • Verify MSBuild import precedence so that Source-specific props (path resolution) still apply correctly on top of the inherited root governance, and that the explicit import above actually pulls the root file in (rather than the auto-import silently selecting only the nearest file).
  • Verification note: after the change, confirm that both the Source and Tests projects observe TreatWarningsAsErrors, WarningLevel, and Nullable from the root file — e.g. inspect the evaluated values via dotnet build -bl / the MSBuild binlog or a preprocessed project (msbuild /pp) — so the governance props are provably inherited and not shadowed.

Consequences

Positive

  • Single SSoT for build policy; Tests now inherit the same strict governance as Source. The Tests project (no child Directory.Build.props) picks up the root file automatically; Source inherits it via the one explicit import.
  • Misconfigured environments fail loudly at build time instead of silently binding to a non-existent default path.
  • RIMWORLD_DIR gives a clear, documented override for any machine.

Negative

  • Accepted risk (LangVersion): with LangVersion=latest and no pin, an SDK bump could shift language semantics — notably field-keyword behavior — under the project. The pin was considered and declined by the user; this drift risk is accepted.
  • Developers must now set RIMWORLD_DIR (or RimWorldDir) before first build; there is no longer a silent default to fall back on.
  • Stricter inherited policy may surface previously tolerated warnings in the Tests project, requiring cleanup before it builds clean.
  • Explicit-import requirement: because MSBuild auto-imports only the nearest Directory.Build.props, Source/Directory.Build.props must carry the explicit GetPathOfFileAbove import or it will shadow the root and silently re-open the governance gap for Source. This import is now a maintained line that must not be dropped; the verification note (both projects see TreatWarningsAsErrors/WarningLevel/Nullable) guards against regression.
  • Build/behavioral note: no source-code API change; this is a build-configuration change. The removed default path is a deliberate behavioral change to the build (fail instead of fall back).

Alternatives considered

  • Pin LangVersion to 13.0 — rejected by the user; keeping latest was preferred despite the accepted SDK-drift risk noted above.
  • Keep governance only in Source/Directory.Build.props and duplicate into the Tests project — rejected: duplication violates SSoT and is exactly the drift that left Tests ungoverned in the first place.

Acceptance criteria satisfied

  • AC-3 — brings the Tests project under zero-warnings + Nullable=enable governance via the repo-root Directory.Build.props (auto-inherited by Tests).
  • AC-2 — removes the machine-specific RimWorld path fallback; RIMWORLD_DIR/RimWorldDir is the documented override and absence fails fast with a clear MSBuild error.
  • AC-5 — establishes the single, consistent TreatWarningsAsErrors + WarningLevel 9999 policy across both Source and Tests required for the zero-warning clean rebuild.
  • Supports AC-1 / AC-4 (Cluster A clean-build closure) by consolidating governance so warning/coverage runs are not misled by drift.
  • Not the LangVersion-pin item — IMP-03 is won't-do per the user's decision (LangVersion=latest retained, SDK-drift risk accepted); no AC requires the pin.

PRD — 004-worktype-widget-map-items

3 goals 6 stories 7 AC 2 non-goals updated 2026-06-07

Problem

The public widget WorkTypeThingRuleWidget can render only one “available items” list in the bottom section of the work-type rule tab. A second list — real on-map Thing instances ranked by the selected rule's stat weights — was previously available to the downstream EquipmentManager mod and is now missing, leaving the widget unable to show players the concrete equipment present on their map.

The bottom section of the tab (DoBottomPart, WorkTypeThingRuleWidget.cs:28-44) currently draws exactly one section header plus one ThingIconBox.DoThingDefBox call over an IReadOnlyList<ThingDef> (List 1, items available by definition). Three coupled limitations block the second list:

  • No public entry for instance data. The public DoWidgetTab(...) (:179-199) carries exactly one items collection (IReadOnlyList<ThingDef> things) and one thing-box scroll position. There is no parameter through which a consumer can supply on-map Thing instances or enable a second list, and no second scroll state.
  • Single-box rendering. DoBottomPart renders exactly one box occupying the full width of the bottom region. The tab's bottom region (Tabs.DoTab, Tabs.cs:45-58) is a fixed, non-scrolling band whose height is sized by GetBottomPartHeight (:206-210) for one box + one section header + one gap. There is no provision for a second list to appear beside the first within that band; today a single list simply takes the whole width.
  • Render primitive present but unwired. The instance-render primitive ThingIconBox.DoThingBox(...) (:39-79) and the instance score path WorkTypeThingRule.GetThingScore(Thing) (:234-242) already exist in the assembly but are dormant — no production caller renders or sorts an on-map Thing list, and no per-instance stat tooltip helper exists.

This sprint restores the second list as an additive capability: the consumer (EquipmentManager) supplies the on-map Thing data, and the widget renders it — sorted by descending score per the rule's stat weights, with a per-instance stat tooltip — alongside the unchanged ThingDef list. Enabling the second list requires a change to the public DoWidgetTab(...) signature, which is permitted (backward_compat: none) and must be documented.

Audience & consumers

  • Mod developers consuming LordKuper.Common — primarily the downstream EquipmentManager mod. EquipmentManager owns the on-map item collection logic and calls DoWidgetTab(...) as its integration point. This sprint gives that consumer a public way to supply on-map Thing instances and enable the second list; EquipmentManager adapts to the changed signature separately (out of scope — see Non-goals).
  • End users (RimWorld players, indirectly) — players using a consuming mod see two ranked lists in the work-type rule tab: items available by definition (List 1) and the concrete equipment present on their current map ranked best-first for the selected rule (List 2). They are not a direct API audience but are the ultimate beneficiary of the restored behavior.
  • In-library render & scoring surface — ThingIconBox.DoThingBox (the dormant instance-render primitive) and WorkTypeThingRule.GetThingScore(Thing) (the instance score path) are the existing building blocks this sprint wires up. Both already exist and are not introduced by this sprint.

Goals

  1. G1

    Restore a second “available items” list in the widget's bottom section that renders real on-map Thing instances, ranked by descending score per the selected rule's stat weights, each with a tooltip showing that instance's actual stat values.

  2. G2

    Expose the second list publicly through WorkTypeThingRuleWidget.DoWidgetTab(...) so the consumer can supply on-map Thing data and enable rendering, preserving List 1 (ThingDef) with no regression and the bottom band's layout with no overlap.

  3. G3

    Document any break to the public DoWidgetTab(...) signature, ship the change by rebuilding and republishing the assembly green (0 warnings) with existing tests passing, and cover the new behavior with tests where feasible.

Open design decisions (owned by the ADR)

Two decisions in this sprint's scope are deferred to the architect and recorded in adr.html. They are listed here as open so requirements traceability is complete; this PRD does not decide them.

  • Public API form (affects AC-1, AC-6) — how the consumer supplies the on-map Thing instances and enables the second list: a DoWidgetTab overload, an optional/added parameter (and a second scroll position), a render-options object, or a separate method. The current 10-parameter signature is the consumer's integration point, so the form should minimize call-site churn. Open in the ADR.
  • Score-sort ownership (affects AC-3) — whether the consumer pre-sorts the Thing instances by score or the widget sorts them via WorkTypeThingRule.GetThingScore. Both score paths intentionally depend on observation order: StatRanges normalization maintains a running, expanding per-stat min/max (WorkTypeThingRule.cs:181-194), so scoring two lists against shared range history normalizes differently than scoring them in isolation. AC-3 requires only relative best-first order within the list. Open in the ADR.

UI / UX

N/A — no web UI and no design-system / UX-spec step for this sprint. The change is to a RimWorld IMGUI widget consumed as a library assembly: a public C# API plus immediate-mode rendering of two list boxes within a fixed bottom band. Functional rendering and layout requirements are captured as acceptance criteria (AC-2, AC-3, AC-4, AC-5) rather than as mockups or flows. Per the precedent sprint (003), this library produces only prd.html + adr.html; no ux-spec.html, mockups, or design-system tokens apply.

Non-goals

  • Changes inside the EquipmentManager mod. The consumer adapts to the new DoWidgetTab(...) signature separately; that work is out of scope for this sprint.
  • The map-item collection logic. Gathering the on-map Thing instances is supplied by the consumer; the widget only renders the supplied data and does not query the map itself.

Documentation follow-ups (non-functional)

No existing documentation describes WorkTypeThingRuleWidget, ThingIconBox, DoWidgetTab, or the bottom-section layout (see audit.md — “Existing docs found: None”). There is therefore no persistent doc to update for the signature break beyond sprint.md and the decisions-log.

The audit flags a candidate persistent public-API reference for this widget (e.g. a design/api/ fragment capturing the post-change public surface, the chosen enable-second-list parameter form, and the score-sort ownership decision). Whether that doc is created now or deferred is a design-promote decision and is owned by the architect / design-promote phase, not this PRD.

XML-doc coverage for the changed public member(s) is handled in implementation, not as a documentation migration.

ADR-0004 · Test framework: xUnit 2.9.3 → NUnit 4.6.1 + NUnit3TestAdapter 6.2.0

Context

Source/LordKuper.Common.Tests (net472) runs on xUnit 2.9.3 with xunit.runner.visualstudio 2.8.2 and a custom xUnit-specific framework seam ([assembly: TestFramework] + RimWorldTestFramework : XunitTestFramework). The audit inventoried 132 [Fact] — 129 executed plus 3 [Fact(Skip=…)] — and 3 [Theory] with 13 [InlineData] rows, plus 236 Assert.* calls across 11 files. The sprint standardizes the suite on NUnit + FluentAssertions for more expressive, diff-rich assertions and a maintainable runner setup (PRD G1, G2; AC-1 … AC-9). The framework choice is the foundational decision: it fixes the attribute model, the runner package, the lifecycle hooks every other ADR in this sprint builds on, and the exact major/minor versions, which interact with the project's net472 target and LangVersion=latest build governance (ADR-0003).

Decision

Replace the xUnit 2.9.3 stack with NUnit 4.6.1 + NUnit3TestAdapter 6.2.0, keeping Microsoft.NET.Test.Sdk 17.14.1, and map the attribute model 1:1.

  • Package swap in LordKuper.Common.Tests.csproj: remove xunit 2.9.3 and xunit.runner.visualstudio 2.8.2; add NUnit 4.6.1 and NUnit3TestAdapter 6.2.0. Keep Microsoft.NET.Test.Sdk 17.14.1 (the NUnit adapter needs the same VSTest host). NUnit3TestAdapter carries the existing runner convention verbatim (PrivateAssets=all; IncludeAssets=runtime; build; native; contentfiles; analyzers; buildtransitive). Swap the global <Using Include="Xunit" /> to <Using Include="NUnit.Framework" /> (FluentAssertions using is added by ADR-0005). The RimWorld <Reference> block, the production <ProjectReference>, and Directory.Build.props inheritance are unchanged (AC-1, AC-3, AC-4).
  • Version rationale — NUnit 4.6.1 (not 3.x). 4.6.1 is the current 4.x release; its framework floor is net462, which net472 satisfies ("4.6.2 or higher"). NUnit 4.6 converted TestDelegate/ActualValueDelegate to Action/Func<T>, which can cause overload ambiguity unless the project compiles with C# 13+; the project builds on .NET SDK 10.0.300 with LangVersion=latest (C# 14), so this is satisfied — and the suite does not use Assert.Throws/Assert.That(..., Throws…) anyway (exception assertions go through FluentAssertions per ADR-0005), so TestDelegate is never referenced. The classic Assert.AreEqual API (removed in 4.0, restored as extension methods in 4.5.0) is irrelevant because no NUnit Assert.* is used.
  • Adapter naming. The adapter package keeps the name NUnit3TestAdapter even when paired with NUnit 4 — the "3" is the adapter/engine lineage, not the framework major. Its assemblies are nunit.framework and NUnit3.TestAdapter, which is why scripts/coverage.ps1's AltCover filter changes --assemblyFilter xunit → --assemblyFilter nunit (AC-27).
  • Attribute mapping (1:1, exhaustive). Three distinct rules, by source attribute:
    • Parameterless [Fact] → [Test]. A method that takes no arguments carries a single [Test] attribute. All 132 [Fact] map this way: 129 executed [Test] + 3 [Test, Ignore] (AC-5).
    • Parameterized [Theory] + N×[InlineData(...)] → N×[TestCase(...)] on the same (now parameterized) method, with NO standalone [Test] attribute on it. Each [TestCase(...)] both declares a runnable case and supplies the arguments for that case, so the set of [TestCase] attributes is the complete and only case-declaring attribute on the method. A bare [Test] must NOT be added to a method that requires arguments: NUnit would treat that [Test] as a zero-argument case it cannot supply parameters for, producing a spurious non-runnable / errored case alongside the legitimate [TestCase] cases. So a parameterized method is annotated with [TestCase(...)] attributes only. The 3 [Theory] methods expand to 13 [TestCase] cases (one per former [InlineData] row); enum-flag expressions like TestFlags.FlagA | TestFlags.FlagB are valid [TestCase] args because they are constant expressions (AC-6, AC-7).
    • Skipped [Fact(Skip="reason")] → [Test, Ignore("reason")] (the 3 sites in Filters/PawnFilterTests.cs, reason "Requires live RimWorld context for Verse.Translator" — kept present and reported as ignored, not deleted, AC-8).
    Case counts are preserved exactly: 129 executed [Test] + 3 [Test, Ignore] (from the 132 [Fact]), plus the 3 [Theory] methods expanding to 13 [TestCase] cases — 142 executed + 3 ignored in total (AC-9), consistent with the PRD inventory table as the single source of truth.
  • Assertion library and infra seam are deferred to ADR-0005 (FluentAssertions), ADR-0006 (resolver seam) and ADR-0007 (StaticState isolation). This ADR owns only the framework/runner/attribute swap.
  • Three new dependencies (NUnit, NUnit3TestAdapter, FluentAssertions) and the removal of two (xunit, runner) are introduced under Complication Approval, pending user approval at the design-review/promote gate; they are the direct, approved scope of sprint 002 (decisions-log 2026-06-04). The contract change is the test-stack swap; production code (Source/LordKuper.Common) is untouched (AC-18).

Consequences

Positive

  • Standardizes the suite on the project's chosen NUnit + FluentAssertions stack; the attribute model maps 1:1, so no test is dropped or semantically changed (AC-9, AC-18).
  • NUnit is non-parallel by default, which removes the need for an explicit serialization marker for the static-state suites (simplifies ADR-0007).
  • Microsoft.NET.Test.Sdk and the runner convention are retained, so dotnet test and the AltCover flow keep working with only a filter-token change.
  • Pinning exact versions (NUnit 4.6.1, adapter 6.2.0) makes the stack reproducible and verifiable against the build governance.

Negative

  • Net new dependency surface: three packages added (two removed). The team now maintains NUnit/adapter/FA version compatibility (4.6.x ↔ 6.x ↔ 7.x) instead of the xUnit v2 lockstep.
  • NUnit 4.6's TestDelegate→Action change is a latent trap: were LangVersion ever pinned below C# 13 (it is latest per ADR-0003), or were Assert.That(..., Throws…) introduced, overload ambiguity could surface as build errors. Mitigated by staying on FluentAssertions for exception assertions and on LangVersion=latest.
  • The custom [assembly: TestFramework] hook has no NUnit analog; the resolver seam must be re-architected (ADR-0006) rather than ported — a behavior-sensitive rewrite, not a swap.
  • Must build warning-clean under ADR-0003's TreatWarningsAsErrors + WarningLevel 9999: any NUnit/adapter analyzer warning or obsolete-API notice fails the build, not just warns. A Release build after migration must surface these before impl-review.
  • The persistent xUnit @ 2.9.3 tech-reference and the stack.html test-stack rows become superseded; the remap is routed through design-promote, not edited in place here.

Alternatives considered

  • Stay on xUnit 2.9.3 — rejected: the sprint's explicit, user-approved goal is to standardize on NUnit + FluentAssertions (decisions-log 2026-06-04). Not a technical failing of xUnit; a deliberate standardization choice.
  • NUnit 3.x instead of 4.x — rejected: 4.6.1 is the current line, supports net472, and the TestDelegate/classic-Assert concerns that motivate some teams to stay on 3.x do not apply here (no NUnit Assert.* use; C# 14 build). Choosing 3.x would adopt an older line for no benefit.
  • MSTest — rejected: not the project's chosen standard; would still require the same resolver/isolation rewrite while offering no advantage over NUnit for this suite.
  • FluentAssertions 8.x license carve-out aside, keep xUnit asserts — out of scope: assertion-library choice is owned by ADR-0005.

Related ADRs

  • ADR-0005: the assertion-library half of the same migration (FluentAssertions 7.x).
  • ADR-0006: re-architects the framework seam this swap removes.
  • ADR-0007: remaps the static-state isolation lifecycle this swap changes.
  • ADR-0003: the TreatWarningsAsErrors / WarningLevel 9999 / LangVersion=latest governance the migrated stack must satisfy.

ADR-0005 · Assertion library: FluentAssertions 7.2.2 (Apache-2.0), not 8.x

Context

The suite holds 236 Xunit.Assert.* calls (12 distinct methods) across 11 files. The sprint converts them to FluentAssertions .Should() form for readable, diff-rich failures (PRD G2; AC-10 … AC-16). Two forces shape the decision: (1) the FluentAssertions license split — version 8.0 moved commercial use to a paid license, while 7.x stays Apache-2.0 — and (2) one xUnit assertion (Assert.Equal(exp, act, precision)) has no 1:1 FluentAssertions equivalent because xUnit's precision is decimal-places while FluentAssertions BeApproximately takes an absolute tolerance.

Decision

Adopt FluentAssertions 7.2.2 (latest 7.x, Apache-2.0) as the sole assertion library, pinned to the 7.x line, and convert every Assert.* per the PRD's assertion-mapping table.

  • Pin to 7.x; reject 8.x. FluentAssertions 8.0+ requires a paid commercial license for commercial use; 7.x "will remain fully open-source indefinitely" under Apache-2.0. Pin FluentAssertions 7.2.2 (latest 7.x, 2026-03-16) and never float to 8.x (AC-1, AC-2). 7.x supports net472.
  • Add the global <Using Include="FluentAssertions" /> so .Should() is implicitly available (mirrors the NUnit/Xunit global-using convention, AC-4).
  • Mapping policy. The per-method Assert.* → .Should() conversion table in the PRD (prd.html §Assertion mapping reference, AC-16) is the single authoritative conversion contract; this ADR does not restate those rows. The ADR owns only the conversion policy that the table does not capture: the FA 7.x pin rationale (below), the Assert.Equal(…, precision) → BeApproximately semantic-shift nuance (next bullet), and the Assert.True/False-over-comparison diff-preservation rule (further below). Collection vs substring overload selection, and the preservation of exception type and any message/inner-exception assertion on Assert.Throws<T> → action.Should().Throw<T>(), follow the PRD table per site (AC-11, AC-14, AC-15).
  • Semantic-shift site — Assert.Equal(exp, act, precision) → act.Should().BeApproximately(exp, tolerance) with tolerance = 10^-precision (e.g. MathHelper precision 4 → tolerance 1e-4). This is not a 1:1 swap: xUnit precision rounds to N decimal places; FA tolerance is an absolute band. Each such site is converted explicitly with the chosen tolerance documented, and boundary/clamp cases (MathHelper normalization) are spot-checked to confirm equivalent pass/fail behavior (AC-12). Any site that cannot map 1:1 is flagged as a reviewable edit (AC-16).
  • Diff-preservation policy (refactor+cleanup mode). When Assert.True/False wraps a value comparison, prefer the value-comparing FA form (x.Should().Be(y)) over the weaker .Should().BeTrue() so the failure diff is preserved; plain boolean checks use .Should().BeTrue()/.BeFalse() (AC-13). Any assertion-strength change (tightening/pruning a weak or redundant assertion, permitted by the approved refactor+cleanup mode) is an explicit, individually reviewable edit — never an accidental side effect of mechanical conversion (AC-17).
  • Introducing FluentAssertions is a new dependency under Complication Approval, pending the user gate; it is the approved scope of sprint 002 (decisions-log 2026-06-04, "FluentAssertions version pinned to 7.x").

Consequences

Positive

  • Readable, diff-rich assertion failures; intent-revealing .Should() syntax across the suite.
  • Apache-2.0 7.x avoids any commercial-license obligation; the pin is explicit and documented so accidental 8.x adoption is guarded.
  • The mapping table makes the conversion mechanical and reviewable for 11 of 12 assert methods; only one method (the precision case) needs judgment, and that judgment is isolated and documented.

Negative

  • The BeApproximately tolerance is a behavioral risk: a wrong tolerance silently loosens or tightens a float assertion, masking or inventing failures. Mitigated by the 10^-precision rule + boundary spot-checks (AC-12), but it is the one place mechanical conversion is unsafe.
  • Version pin is a standing maintenance constraint: dependabot/NuGet auto-update to 8.x must be actively prevented; 7.x receives only bugfixes, so the suite forgoes future 8.x assertion features.
  • New dependency surface (one package) the team must keep warning-clean under ADR-0003; any FA analyzer/obsolete warning fails the build under WarningLevel 9999 and must be resolved, not blanket-suppressed.
  • Refactor+cleanup mode widens the diff beyond a pure mechanical swap, raising review effort — the AC-13/AC-17 "explicit reviewable edit" rule is the control that keeps it auditable.

Alternatives considered

  • FluentAssertions 8.x (latest) — rejected: commercial license for commercial use; 7.x is the last Apache-2.0 major and is the explicit user decision (decisions-log 2026-06-04).
  • NUnit's built-in constraint model (Assert.That(...)) — rejected: would re-introduce the NUnit Assert/TestDelegate surface this migration deliberately avoids, and offers a less diff-rich failure message than FluentAssertions for the equality-heavy suite (~108 Assert.Equal sites).
  • Shouldly — rejected: another new dependency with no advantage over FluentAssertions for this suite; not the project's chosen standard.
  • Keep Xunit.Assert alongside NUnit — rejected: would retain a transitive xUnit reference purely for assertions, defeating the framework swap and the stack simplification.

Related ADRs

  • ADR-0004: the framework half of the same migration; together they define the full new test stack.
  • ADR-0003: the warning-clean build gate the FA usings and converted asserts must pass.

ADR-0006 · RimWorld AssemblyResolve seam: [assembly: TestFramework] → global [SetUpFixture]

Context

Most of the suite references RimWorld/Unity types. The library does not ship those assemblies; it references them with <Private>False</Private> so they are not normally copied to the test output. Under xUnit, resolution was wired entirely through the framework-swap hook ([assembly: TestFramework("…RimWorldTestFramework", …)] in AssemblyInfo.cs + RimWorldTestFramework : XunitTestFramework, whose constructor calls InitializeRimWorldResolver() before any discovery) registering an AppDomain.CurrentDomain.AssemblyResolve handler that loads the DLLs from the RimWorld install at runtime. NUnit has no analog to [assembly: TestFramework]. The load-bearing constraint is timing: NUnit's engine reflects over the test assembly at discovery time — it calls Assembly.GetTypes() and GetCustomAttributes(true) while building its fixture model — and a runtime AssemblyResolve handler registered by any NUnit lifecycle hook fires too late for that reflection-only scan. If the RimWorld/Unity dependency chain (including netstandard 2.1, which RimWorld ships but net472 lacks in the GAC) is not present in the test bin at discovery time, the test assembly is marked NotRunnable and zero tests are discovered, presenting as mass test failure rather than a wiring bug (audit risk; PRD AC-19 … AC-21). The coverage harness (scripts/coverage.ps1) reads from the same test bin when AltCover instruments and when NUnit re-scans during the instrumented test run, so it depends on the same DLLs being present.

Reconciliation note — 2026-06-04 (sprint 002 impl-review iter-02). This ADR was updated to describe the as-built implementation. The discovery-time ordering risk previously flagged as "asserted, not proven" was resolved in practice by making the RimWorld/Unity DLLs present in the test bin at discovery time (an MSBuild copy-local target), so resolver-registration timing is no longer the load-bearing guarantee. The phantom "idempotency guard retained" claim and the "delete copied DLLs after instrumentation" coverage step were removed (neither exists in the built code), and the [ModuleInitializer] "anticipated fallback" framing was demoted to a considered-and-rejected alternative.

Decision

Replace the xUnit framework-swap hook with a two-part as-built mechanism: (1) a PRIMARY CopyRimWorldTestDeps MSBuild target that copies the RimWorld/Unity managed DLLs into the test output so they are present (copy-local) when NUnit reflects over the assembly at discovery time, and (2) a FALLBACK runtime AssemblyResolve handler registered by a namespace-less (global) [SetUpFixture] / [OneTimeSetUp], preserving the resolution contract verbatim.

  • Primary — copy-local at build time (CopyRimWorldTestDeps). The RimWorld <Reference> items in LordKuper.Common.Tests.csproj carry <Private>False</Private>, which keeps them out of the normal copy step. An MSBuild target CopyRimWorldTestDeps (AfterTargets="Build") explicitly copies Assembly-CSharp.dll, Assembly-CSharp-firstpass.dll, UnityEngine.CoreModule.dll, UnityEngine.IMGUIModule.dll, UnityEngine.TextRenderingModule.dll, and netstandard.dll (RimWorld's v2.1.0.0 — needed because net472 only has netstandard 2.0 in the GAC) from $(RimWorldManagedDir) into $(OutputPath). These DLLs are then present in bin when NUnit's engine calls Assembly.GetTypes() / GetCustomAttributes(true) during discovery — which is the load-bearing guarantee that the assembly is Runnable and its fixtures are discovered (AC-19, AC-20).
  • Fallback — runtime resolver via global [SetUpFixture]. Delete the [assembly: TestFramework(...)] attribute and the RimWorldTestFramework : XunitTestFramework type; re-house the resolver in a namespace-less [SetUpFixture] (RimWorldResolverSetup). A [SetUpFixture] declared outside any namespace applies to the whole assembly; its [OneTimeSetUp] runs once before any test in the assembly is executed. It fails fast with an actionable message if neither RIMWORLD_DIR nor RimWorldDir is set (or the RimWorldWin64_Data\Managed dir is missing), then registers an AppDomain.CurrentDomain.AssemblyResolve handler. This is the secondary path: it covers any RimWorld/Unity assembly needed at execution time that the copy-local set does not already place in bin (AC-19).
  • Ordering risk resolved in practice. The external (Codex) review had flagged that [OneTimeSetUp] runs at NUnit execution time and does not provably precede discovery-time type loading, so an earlier draft recorded the resolver-before-type-load ordering as "asserted, not proven." The as-built design sidesteps that gap entirely: because the copy-local DLLs are already in bin at discovery time, the timing of resolver registration is no longer load-bearing for discovery. The [OneTimeSetUp] handler remains as a runtime fallback, not the primary guarantee.
  • Resolution contract preserved verbatim (AC-20): the fallback handler's assembly-name match set (Assembly-CSharp, Assembly-CSharp-firstpass, UnityEngine*, Unity.Burst, Unity.Collections, Unity.Mathematics, com.rlabrecque.steamworks.net); the env-var lookup (RIMWORLD_DIR/RimWorldDir); the Managed\<name>.dll Assembly.LoadFrom resolution; and the null-for-everything-else contract are unchanged from the prior implementation. There is no AppDomain.GetData/SetData idempotency guard and no [ModuleInitializer] — the [OneTimeSetUp] hook runs once per process, so no cross-path guard is needed.
  • Verification. Confirm fixtures are discovered and resolve cleanly by running the RimWorld-typed suites (StatWeightTests, RimWorldTimeTests, PawnFilterTests) with no FileNotFoundException/ TypeLoadException and a non-zero discovered-test count (AC-21), and by re-running scripts/coverage.ps1 end-to-end. The coverage script keeps the copied RimWorld DLLs in bin throughout (the earlier post-instrument delete step was removed) because both AltCover instrumentation and NUnit's instrumented re-scan need them present (AC-27).
  • Neither the CopyRimWorldTestDeps target nor the [SetUpFixture] is a new abstraction — the target is a standard MSBuild copy step and the fixture is the NUnit-idiomatic replacement for an existing seam; the resolver logic is reused. No Complication Approval beyond the framework swap (ADR-0004) is required.

Consequences

Positive

  • Makes test discovery deterministic: the copy-local DLLs are present in bin before NUnit reflects over the assembly, so the discovery-time ordering gap the external review flagged is closed by construction rather than asserted.
  • Removes the xUnit-only [assembly: TestFramework] coupling; the fallback resolver is now expressed in plain NUnit constructs ([SetUpFixture]/[OneTimeSetUp]) that any maintainer can read, and the runtime resolution contract is preserved verbatim.
  • The coverage harness works because the same copied DLLs stay in bin for both AltCover instrumentation and NUnit's instrumented re-scan.

Negative

  • Two coupled mechanisms to maintain. The copy-local set in CopyRimWorldTestDeps must stay in sync with what NUnit's discovery actually needs (it currently includes netstandard.dll 2.1 because Assembly-CSharp and the UnityEngine modules reference it and net472 lacks it in the GAC). If a future test references a RimWorld/Unity assembly not in the copy list and not caught by the fallback handler's name match, discovery can regress to NotRunnable.
  • Namespace placement of the fallback fixture is still a hard requirement. If the global [SetUpFixture] is accidentally placed inside a namespace, it scopes to that namespace only; the fallback would then not cover the whole assembly. The namespace-less placement is required, not a style choice.
  • The fallback handler mutates process-global AppDomain state. It is registered exactly once via [OneTimeSetUp] (which NUnit runs once per assembly per process), so no idempotency guard is needed; there is none in the as-built code.
  • The copy-local DLLs increase the test bin footprint and are kept there for the whole coverage run (no post-instrument delete), which AltCover must be told to ignore via --assemblyFilter entries for UnityEngine, Assembly-CSharp, and netstandard.
  • Supersedes the XunitExtensions.cs/AssemblyInfo.cs wiring; the rename + attribute deletion plus the new MSBuild target are behavior-sensitive edits that must be verified by actually running the RimWorld-typed suites and the coverage script, not by inspection alone.

Alternatives considered

  • Runtime AssemblyResolve alone (no copy-local DLLs) — rejected: a handler registered by any NUnit lifecycle hook fires too late for the reflection-only scan NUnit performs at discovery (GetTypes()/GetCustomAttributes(true)), so the assembly is marked NotRunnable and zero tests are discovered. Copy-local at build time is what actually makes discovery succeed; the runtime handler is retained only as an execution-time fallback.
  • Module initializer ([ModuleInitializer] + net472 attribute polyfill) — considered and rejected as unnecessary. It would register the resolver at module load, earlier than [OneTimeSetUp], but the copy-local approach already guarantees the DLLs are present at discovery, so the earlier registration buys nothing; it would add a net472 polyfill and is harder to verify. Not adopted.
  • Per-fixture [OneTimeSetUp] on each RimWorld-typed test class — rejected: duplicative, easy to forget on a new test class (silent regression), and still per-class rather than assembly-global; the single global fallback fixture is the minimal, centralized seam.

Related ADRs

ADR-0007 · StaticState isolation: xUnit [Collection]/IDisposable → NUnit [SetUp]/[TearDown] + [NonParallelizable]

Reconciliation note — 2026-06-04 (sprint 002 impl-review iter-02). This ADR was updated to describe the as-built implementation. There is no StaticStateFixture type in the built code: the snapshot/restore logic is inlined directly into StaticStateTestBase's [SetUp]/[TearDown]. The captured-state set and the [NonParallelizable] serialization are unchanged.

Context

Three test classes (StatWeightTests, StatefulSubsystemTests, StatRangesTests) touch shared static caches and isolate via the xUnit seam introduced in ADR-0001: a StaticStateFixture : IDisposable snapshotted DefProvider.Current and restored it (rebuilding StatHelper, WorkTypeStatMap, and reflection resets of SkillStatMap._map, PassionHelper.{_isInitialized,_cachedPassions,PassionCache}, StatRanges.Ranges); StaticStateTestBase drove it per-test via ctor + Dispose; and a [CollectionDefinition("StaticState", DisableParallelization=true)] + [Collection("StaticState")] serialized the classes. ADR-0001 was deliberate that per-test ctor+Dispose (not per-class IClassFixture) gives true per-test isolation. The migration must preserve the isolation contract (the exact snapshot/restore set) while re-expressing the xUnit lifecycle vocabulary in NUnit (PRD AC-22 … AC-25). This makes ADR-0001's xUnit-specific prose inaccurate; that ADR is approved and persistent, so its wording must be remapped through design-promote, not edited here.

Decision

Re-express the ADR-0001 isolation seam in NUnit: keep the snapshot/restore body verbatim, inline it directly into StaticStateTestBase, drive it from per-test [SetUp] (snapshot) / [TearDown] (restore), and replace the xUnit collection-serialization with NUnit's default non-parallel execution (made explicit via [NonParallelizable]).

  • Snapshot/restore preserved verbatim (AC-22): the set of snapshotted/restored statics — DefProvider.Current (captured in [SetUp], restored in [TearDown]); rebuild of StatHelper and WorkTypeStatMap; reflection resets of SkillStatMap._map, PassionHelper.{_isInitialized,_cachedPassions,PassionCache}, and StatRanges.Ranges — is unchanged. This body is framework-agnostic and is the actual isolation contract from ADR-0001 (and the StatRanges.Ranges entry exists because ADR-0002 keeps that cache mutable). The as-built form has no separate StaticStateFixture type: the snapshot/restore logic lives inline in StaticStateTestBase's [SetUp]/[TearDown] methods, which is simpler than carrying a dedicated disposable fixture type and is sufficient because the base class is the only consumer.
  • Per-test lifecycle remap (AC-23): StaticStateTestBase's constructor → [SetUp] (capture _originalProvider = current provider); its Dispose() → [TearDown] (restore the provider, then rebuild/reset the dependent caches). NUnit [SetUp]/[TearDown] are per-test, matching the original ctor+Dispose per-test granularity exactly — the deliberate ADR-0001 choice over per-class IClassFixture is preserved.
  • Serialization remap (AC-24): drop [CollectionDefinition("StaticState", DisableParallelization=true)] and [Collection("StaticState")]. NUnit runs non-parallel by default (this project sets no [Parallelizable]/[assembly: Parallelizable]), so the static-touching classes are already serialized. Apply [NonParallelizable] to the three classes anyway, as an explicit, self-documenting statement of intent (belt-and- suspenders against a future accidental opt-in to parallelism).
  • Supersession of ADR-0001 vocabulary. This ADR supersedes the xUnit-specific wording of ADR-0001 (StaticStateFixture via IClassFixture, [Collection] serialization, IDisposable snapshot/restore) — not ADR-0001's isolation contract or its IDefProvider/InternalsVisibleTo decisions, which stand unchanged. The actual edit to the approved, persistent adr-0001-…html is performed in design-promote (remap the vocabulary in place, contract untouched), never silently here. ADR-0001 is not marked superseded as a whole; only its mechanism prose is updated.
  • No cross-test bleed (AC-25): running the full suite repeatedly and in any order yields the same results; the 8 plain (non-isolated) classes are unaffected by the seam.
  • The InternalsVisibleTo grant and the internal reset/snapshot hooks from ADR-0001 remain in force; this remap introduces no new abstraction, layer, or dependency, so no fresh Complication Approval is needed.

Consequences

Positive

  • Isolation contract is preserved bit-for-bit; only the lifecycle vocabulary changes, so the risk of altering what the suite verifies is minimal.
  • NUnit's non-parallel-by-default removes the need for an explicit serialization construct; [NonParallelizable] is documentation, not load-bearing wiring — simpler than the xUnit collection machinery.
  • Per-test [SetUp]/[TearDown] map 1:1 to the original per-test ctor+Dispose, keeping the deliberate per-test (not per-class) granularity from ADR-0001.

Negative

  • Approved-ADR drift: ADR-0001 (approved, persistent) now describes the seam in vocabulary the code no longer uses. Until design-promote remaps its wording, the persistent doc is partly inaccurate. Mitigation: route the wording update through design-promote, keep the contract unchanged so only mechanism prose moves.
  • Relying on NUnit's non-parallel default is implicit: if anyone later adds [Parallelizable] at assembly scope, the static-state suites would race and the snapshot/restore isolation would break. [NonParallelizable] on the three classes is the explicit guard, but a global parallel opt-in could still mis-order setup; the tech-reference notes "do not add [assembly: Parallelizable]".
  • The reflection-driven reset set is a maintained contract: if production adds a new static cache, the snapshot/restore set must be extended in lockstep or new cross-test bleed appears — same standing obligation as under xUnit, carried forward unchanged.
  • The StaticStateTestBase ctor→[SetUp] / Dispose→[TearDown] rewrite is behavior-sensitive (ordering of snapshot vs. test body); must be verified by repeated/random-order full runs (AC-25), not inspection.

Alternatives considered

  • Per-class [OneTimeSetUp]/[OneTimeTearDown] (snapshot once per class) — rejected: coarsens isolation to per-class, reversing ADR-0001's deliberate per-test choice; a test that mutates statics could then leak into the next test in the same class.
  • Keep a serialization marker analogous to [Collection] (e.g. an explicit single-threaded fixture) — rejected: redundant given NUnit's non-parallel default; adds machinery for no behavioral gain.
  • Mark ADR-0001 fully superseded and re-state the whole isolation decision here — rejected: ADR-0001's contract (IDefProvider, the snapshot set, InternalsVisibleTo) is unchanged and still authoritative; only the mechanism vocabulary moves, so a scoped vocabulary remap (via design-promote) is correct, not a wholesale supersession.
